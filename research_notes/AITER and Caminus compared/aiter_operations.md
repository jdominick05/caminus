# AITER operators and Caminus integration

## What overlaps at the operator level

### Takeaway

AITER now covers much of the same mathematical territory as Caminus, including QSA and Qwen3-Next Gated DeltaNet, and it contains actual persistent MoE megakernels. The important differences are execution scope, numerical/state contracts, weight formats and per-operator hardware coverage. This is not a comparison between a kernel-free server and a kernel library: Caminus already implements its own GPU execution architecture. [AITER QSA](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/attention/qsa.py); [AITER fused GDN decode](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/gated_delta_net/fused_gdn_decode_qkvz.py#L4-L28); [Caminus architecture](../../docs/dev/architecture.md)

### Cited findings

- Snapshot: AITER `main` resolved to `37da1dbeb305e868dda2e52d0d084a30fd71a99c`, committed 2026-11-12 16:54:25 UTC. All upstream links below use that SHA. The inspected local Caminus HEAD was `25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62`; local source links refer to the working tree. This was a source-only investigation: no kernel builds, installations or GPU measurements. [AITER commit](https://github.com/ROCm/aiter/commit/37da1dbeb305e868dda2e52d0d084a30fd71a99c)

- **Attention:** `unified_attention` takes query rows, sequence lengths, block tables and a sliding-window argument, with separate 2D/3D and split-KV dispatch. Current sources contain explicit gfx1100 unified-attention and paged-decode configurations; old reports of missing architecture configurations cannot be treated as present-day proof of universal incompatibility. These are callable operator entrypoints, not a conversation lifecycle or cache-retention service. [Unified attention interface](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/attention/unified_attention.py#L427-L495); [gfx1100 unified-attention configuration](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/configs/gfx1100/triton/attention/unified_attention/DEFAULT.json); [gfx1100 paged-decode configuration](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/configs/gfx1100/triton/attention/pa_decode/DEFAULT.json)

- **QSA is a particularly close match:** AITER implements compressed-key scoring, expansion of selected compressed groups into token IDs plus the causal tail, and sparse paged GQA. `compress_ratio` defaults to four. It supports unquantized, FP8 per-row and MXFP4 compressed-key cache formats. Sparse GQA supports unquantized or FP8 KV, not Caminus's GGUF-style Q8_0 cache representation. The scoring wrapper has a fallback path when an architecture lacks QSA tuning. Caminus independently implements indexer projections, raw keys, four-token pooled keys, scoring, selection and selected-cell attention inside K3. [AITER QSA APIs](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/attention/qsa.py#L273-L305); [AITER sparse GQA](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/attention/qsa.py#L529-L616); [Caminus QSA wiring](../../python/caminus/engine/flashnext_tp.py)

- **Gated DeltaNet:** the generic Triton API exposes recurrent and chunked gated delta rules, variable-length sequences, optional initial/final states, and transposed `[V,K]` state variants. The HIP chunk-state wrapper fixes chunk size at 64 and requires BF16 `k`, `w` and `u`, although state can be FP32 or BF16. Caminus's q35 prefill runs its decode recurrence statements in sequence over the chunk to preserve its specified order and state handoff. AITER's chunk algorithm is consequently a meaningful algorithmic alternative, not automatically a numerically interchangeable drop-in. [Generic GDN interfaces](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/gated_delta_net/gated_delta_rule.py#L39-L58); [Chunk-state contract](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/chunk_gated_delta_rule_fwd_h.py#L200-L251); [Caminus q35 prefill](../../python/caminus/prefill/q35own.py)

- **Do not equate KDA with Qwen GDN:** AITER's fused Qwen3-Next GDN explicitly documents differences in gating, output activation, biased convolution and value/key head ratios. Its ratio-generic path includes ratio three for Qwen3.5/3.8-27B, but the fused implementation explicitly accepts only gfx950 because it uses CDNA buffer addressing, inline assembly and explicit layouts. A report that KDA runs on RDNA3 is not evidence that this fused GDN does. Its highly specialized fused prefill is gfx950-only too. [Fused GDN distinctions and architecture gate](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/gated_delta_net/fused_gdn_decode_qkvz.py#L4-L28); [Prefill support](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/gated_delta_net/fused_gdn_prefill_qkvz.py#L4-L35)

- **Convolution:** causal-conv update supports a maintained history, optional circular indexing via `cache_seqlens`, physical state-slot indices and padding-slot skips. That is useful state machinery for hybrid models, although it is a convolution-state window rather than the model's full rolling attention context. [Conv update contract](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/causal_conv1d_update.py#L12-L58)

- **MoE:** routing, sorting, expert-stage GEMMs and reductions are all present. There are backend-specific CK and ASM paths plus Triton/FlyDSL paths. In particular, Triton `moe_gemm_a16w4` means 16-bit activations with **MXFP4** weights: packed E2M1 values and E8M0 block scales, with column-major requirements. It does not mean an arbitrary four-bit weight format. [MoE entrypoints and quantization dispatch](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/moe_op.py); [MoE a16w4 representation](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/moe/moe_op_gemm_a16w4.py#L338-L430)

- **There is also genuine groupwise INT4 GEMM on gfx1100:** `gemm/basic/gemm_a16w4.py` instead uses packed uint4 and `W[n,k] = (q[n,k] - zero[n,g]) * scale[n,g]`, with integer zero points, FP16/BF16 activations and GPTQ/AWQ conversion helpers. Its documentation explicitly lists gfx942 and gfx1100. This distinct API is closer to ordinary weight-only INT4, but still does not decode Q4_K/Q6_K or IQ codebooks. Treating all `a16w4` names as the same format would be wrong. [INT4 GEMM contract](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/gemm/basic/gemm_a16w4.py#L20-L62); [Caminus own-format constants and layouts](../../python/caminus/engine/k3.py)

- **Dense FP16/BF16 GEMM is another realistic seam:** current gfx1100 default and shape-specific configurations exist for `gemm_a16w16`. Its API consumes FP16/BF16 matrices, while Caminus's memory-constrained models keep most weights in GGUF quantized form. Therefore its natural first target is an existing unquantized BF16/FP16 projection or an isolated experiment, not expanding all quantized weights to 16-bit. [GEMM interface](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/gemm/basic/gemm_a16w16.py#L77-L136); [gfx1100 configs](https://github.com/ROCm/aiter/tree/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/configs/gfx1100/triton/gemm/gemm_a16w16)

- **Norm/RoPE fusion:** there are FP16/BF16/FP32 RMSNorm operators, fused residual-add variants, and fused Q/K RMSNorm + RoPE + writes into shuffled paged KV, with optional quantization. Inputs, cache layouts and rounding need matching; mathematical similarity does not establish Caminus's required bitwise equivalence. [RMSNorm contracts](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/rmsnorm.py#L13-L194); [QK/RoPE/cache fusion](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/fused_qk_norm_rope_cache_quant.py#L52-L114)

### Inferences

- Direct integration should start at an existing independent prefill launch. Replacing individual K3 operations with Python calls would change the execution model and reintroduce launches; a source port into K3 must instead fit the tape, its dependency protocol and shared register allocation. This follows from Caminus's whole-model persistent pass and its separately launched prefill APIs. [Caminus architecture](../../docs/dev/architecture.md); [Prefill launch wrappers](../../python/caminus/prefill/q35own.py)
- Repacking existing weights without changing their represented values is different from requantizing to MXFP4 or generic INT4. The latter would be a new numerical/model-storage experiment, requiring accuracy and capacity evidence; an `a16w4` label alone does not make it compatible. [INT4 equation](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/gemm/basic/gemm_a16w4.py#L32-L47); [Caminus quantized-math contract](../../docs/specs/spec-own-quant.md)

### Gaps

- No end-to-end Caminus/AITER latency or accuracy comparison was run. Operator availability/config files establish candidates, not speedups or complete reliability on the user's cards.
- No complete proof that every AITER backend lacks every GGUF format was attempted. The inspected matrix/operator interfaces do not provide the GGUF representations Caminus currently consumes; the upstream recursive tree showed no GGUF/Q4_K/Q6_K/IQ-format entrypoint names.

## Persistent execution, communication and rolling context

### Takeaway

AITER is moving into the same broad direction of fusing compute and communication, but its persistent MoE layer is not Caminus's full-model persistent decode tape. Attention primitives can help with the proposed rolling-context work, yet they do not supply the required lifetime position, cache, recurrent-state and client contracts. [MegaMoE TP](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/flydsl/mega_moe_tp.py#L3-L40); [Caminus engine](../../docs/dev/architecture.md); [Live state](../../python/caminus/cache/livestate.py)

### Cited findings

- AITER `MegaMoeTP` executes an entire tensor-parallel MoE layer's GEMM1/activation/GEMM2 and surrounding collectives in one persistent launch. It supports replicated-in/all-reduced-out or sequence-parallel modes. Its documented contract specifies gfx950, MXFP4 shuffled weights, one CTA per CU, exclusive use of the GPU, a two-second device watchdog and sticky error/reset state. It has a large-batch SDMA/MORI path. This is concrete execution-model overlap, not just the word “fused.” [MegaMoE contract](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/flydsl/mega_moe_tp.py#L3-L40)

- Caminus keeps all layers and all operation kinds of one decode/verify pass in K3, with a 96-VGPR/no-spill budget and per-op time-bounded waits. Its two-card exchange writes FP32 partials over PCIe and adds card zero first on both cards. Replacing that with a standalone layer collective changes launch count, synchronization and potentially arithmetic order. [Architecture](../../docs/dev/architecture.md); [Two-card exchange source](../../kernels/k3_xchg.h); [Repository invariants](../../AGENTS.md)

- AITER communication is **not universally XGMI-only**. The generic custom-allreduce signal structure explicitly avoids peer atomics because PCIe does not support them, uses HIP IPC and has FP32/FP16/BF16 dispatch. Its Python integration nevertheless contains platform/topology assumptions, and its newer Lamport path is gated to gfx942/gfx950 and described as wave64. MegaMoE TP's own support gate is gfx950. Do not turn either fact into an unsupported assertion that the whole library either works or cannot work over the user's PCIe link. [PCIe signal comment](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/csrc/include/custom_all_reduce.cuh#L48-L55); [Allreduce dtype dispatch](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/csrc/kernels/custom_all_reduce.cu#L166-L207); [Lamport architecture gates](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/dist/device_communicators/custom_all_reduce.py#L293-L313)

- AITER unified attention's `sinks` argument is a per-query-head tensor. Its kernel uses these values to initialize softmax maxima and normalization mass; it is **not a list of permanently retained prefix-token KVs**. Thus seeing `sinks=` does not establish StreamingLLM-style retained system tokens. [Argument check](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/attention/unified_attention.py#L488-L495); [Sink implementation](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/_triton_kernels/attention/unified_attention.py#L228-L244)

- A sliding attention mask and paged block table provide mechanisms for selecting accessible KV. Caminus still needs a retention policy, logical/physical position separation, RoPE policy, QSA expiration, speculative-write headroom, checkpoint/window mappings and client behavior to implement rolling conversation context. Its existing cache explicitly assumes append-only rows by position, and its live log length equals the processed position. [AITER attention interface](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/attention/unified_attention.py#L427-L495); [Caminus prompt-cache assumptions](../../python/caminus/cache/prompt.py); [Caminus live-state invariant](../../python/caminus/cache/livestate.py)

### Inferences

- AITER is relevant as a source of designs and targeted kernels, not as a drop-in answer to rolling context or a replacement for Caminus's session/cache engine. A page allocator and window mask address only some of the obligations visible in the local state contracts. [Prompt cache](../../python/caminus/cache/prompt.py); [AITER attention](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/attention/unified_attention.py)
- The two-second persistent-layer watchdog cannot be imported unchanged into the repository's GPU-safety contract, which specifies waits around 200 ms and launches well below 200 ms. Likewise, a global exclusive-GPU requirement has to be evaluated against the display-card machine. [AITER timeout contract](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/flydsl/mega_moe_tp.py#L18-L24); [Caminus GPU rules](../../AGENTS.md)

### Gaps

- No custom-allreduce run was performed on the user's two-card PCIe topology; throughput claims from CDNA/XGMI cannot be transferred to it.
- No claim is made that AITER's whole repository cannot implement a higher-level rolling policy elsewhere; the inspected attention APIs do not themselves own that policy.

## Ranked opportunities and evidence required

### Takeaway

Prioritize experiments at existing prefill/attention boundaries and study portable algorithmic improvements. Whole-library dependency adoption, requantizing the catalog and replacing K3 with per-op dispatch should not be assumed worthwhile without end-to-end evidence. The ranking below is an engineering inference from the source contracts above, not benchmark results. [Caminus prefill](../../python/caminus/prefill/q35own.py); [Quantized-math gates](../../docs/specs/spec-own-quant.md)

### Inferences

- Generic INT4 or MXFP4 is a separate model-storage project rather than a first reuse opportunity for this catalog. AITER having low-bit kernels does not remove the need for Caminus's native GGUF decode, IQ codebooks and format-specific prefill. [INT4 contract](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/gemm/basic/gemm_a16w4.py#L32-L62); [MoE MXFP4 contract](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/moe/moe_op_gemm_a16w4.py#L363-L381); [Local quant formats](../../python/caminus/engine/k3.py)
- For all candidates, evaluate the actual final execution mode: eager vs graph, prefill vs decode, same active context, same batch, same memory residency and same hardware. Preserve bitwise gates when feasible; changed quantized math requires the repository's accuracy/model/self/speed gates. An operator speedup alone is insufficient evidence that the whole engine improves. [Caminus quantized-math requirements](../../docs/specs/spec-own-quant.md); [Repository measurement rules](../../AGENTS.md)

### Gaps

- Ranking is provisional because there is no new local profile identifying the currently dominant prefill or decode operation for the user's target workload.
- All proposed adapters and ports remain unimplemented. This research only adds this notes file.
