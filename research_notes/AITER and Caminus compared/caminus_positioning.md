# Caminus positioning relative to AITER

## What layer does Caminus occupy, and what is its actual operating envelope?

### Takeaway

Caminus is an end-to-end, low-concurrency inference engine and service specialized for selected Qwen-derived models on gfx1100. AITER is an operator library that such engines can integrate; overlap exists in GPU math, but the projects do not replace the same complete layer of the stack. [Caminus architecture](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md#L7-L22) [AITER introduction](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/README.md)

### Cited Findings

- Local inspection is at Caminus commit `25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62`, with no changes reported by `git status --short` at the start of this investigation. Its remote is `https://github.com/jdominick05/caminus`. The coordinator supplied the upstream AITER snapshot `37da1dbeb305e868dda2e52d0d084a30fd71a99c`; AITER license and submodule metadata were fetched explicitly at that ref. [Caminus commit](https://github.com/jdominick05/caminus/commit/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62) [AITER commit](https://github.com/ROCm/aiter/commit/37da1dbeb305e868dda2e52d0d084a30fd71a99c)
- The Caminus application owns OpenAI/Anthropic HTTP interfaces, templates, tool parsing, sampling, the session, conversation caching/checkpoints, prompt prefill, the decode engine and drafters, as well as card placement and memory projection. These are engine/application responsibilities above an operator library. [Architecture lines 9–22, 42–70](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md#L9-L70)
- The actual serving worker explicitly processes one request at a time from a FIFO queue and describes its contract as one live sequence, batch 1. Accepting concurrent HTTP connections or retaining parked conversations is not the same as continuously batching multiple active decode sequences. [Worker lines 1–14](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/serve/worker.py#L1-L14)
- Caminus advertises early-testing status and says it has been tested on exactly one machine, an RX 7900 XTX plus RX 7900 XT on Linux. Its hardware table lists these as tested, other gfx1100 products as untested, and other GPU architectures unsupported. [README lines 22–25, 51–61](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/README.md#L22-L61)
- The catalog contains eight served models: Qwen3.8-Flash-Next Coder, two Qwen3.6-35B-A3B variants, AREX-2, Qwen3-Coder-Next, Swift 1.5, ThinkingCap and Qwen3-30B-A3B. These are Qwen families or derivatives, with an architecture registry selecting engine, prompt path, drafter and card count. Do not imply arbitrary transformer compatibility. [Model catalog](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/models.py#L82-L102) [README model constraints](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/README.md#L68-L90)
- AITER's introduction calls it AMD's AI operator library, with C++/Python interfaces and Triton, CK and assembly backends for inference and training. Its own ecosystem table identifies vLLM/SGLang integrations and distinguishes ATOM as an engine built on it. This supports comparing Caminus with an engine using AITER, rather than treating AITER alone as an HTTP-serving alternative. [AITER README](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/README.md)
- Current AITER README explicitly lists Pro W7900/gfx1100 RDNA3 as experimental and states that Triton, most FlyDSL kernels and most HIP kernels run on RDNA, with most CK/ASM kernels restricted to CDNA. Thus “AITER is CDNA-only” is an inaccurate blanket statement. This table does not itself qualify the exact XTX+XT pair, every kernel, or Caminus's model formats. [AITER hardware table and footnote](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/README.md)

### Inferences

- A precise description is: **Caminus is a specialized full inference stack whose kernel layer partly overlaps AITER; AITER can be a source of individual operators, design techniques and comparison baselines.** A wholesale library substitution would still leave Caminus responsible for loading models, maintaining recurrent/cache state, scheduling requests, formatting outputs and enforcing hardware safety. [Caminus architecture](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md) [AITER README](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/README.md)
- Hardware targeting is a real difference, but no longer a binary division between Radeon and Instinct. Caminus is deeply specialized and directly tested on its selected Radeon pair, whereas AITER now has a broader but operator-dependent experimental gfx1100 path. Broadly dismissing AITER as inapplicable would miss current upstream work. [Caminus hardware scope](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/README.md#L51-L61) [AITER hardware scope](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/README.md)

### Gaps

- No AITER operators or alternative AITER-backed engines were installed or benchmarked in this investigation. No throughput, latency or reliability superiority versus AITER has been established. Existing Caminus published numbers compare with llama.cpp, not AITER. [Caminus benchmark description](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/README.md#L75-L87)
- Model coverage and official supported architectures do not prove every advertised operator functions on every model/card combination. The architecture and operator researchers have the detailed per-operator support evidence; this note does not independently establish exact RX 7900 XT/XTX qualification.

## What is distinctive about K3 execution, numerics and existing dependencies?

### Takeaway

K3's organizing unit is a whole-model decode/verify pass represented as a persistent device tape. Its integration constraints are the fixed register budget, dependency/time-bound protocol, exact cache/recurrent semantics and numerical gates; standalone operator speed is insufficient evidence of an improvement. Caminus uses PyTorch for runtime resources while supplying its own HIP compute paths. [K3 architecture](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md#L25-L40) [HIP bridge](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/device/hip.py#L1-L8)

### Cited Findings

- K3 builds a tape of dependent matrix-vector products, attention, normalization and routing tasks. Persistent workgroups claim tasks and synchronize through memory counters with bounded waits. Model-specific compiled modules include only their required operations and formats because all operations share the persistent kernel's register allocation. The documented bound is 96 VGPRs and no VGPR spills. [Architecture lines 25–40](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md#L25-L40) [Register evidence requirement](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/AGENTS.md#L153-L156)
- “One launch per pass” is the target persistent-kernel organization on each participating GPU, not one launch for a whole HTTP request and not a claim that drafters, prefill and recovery use no additional launches. `FlashNextTP` creates one `k3.Engine` per card, and `Engine.run` launches `k3_run` with `hipModuleLaunchKernel`. [Per-card engines](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/engine/flashnext_tp.py#L403-L420) [Launch code](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/engine/k3.py#L1393-L1426)
- Two-card decode performs tensor-parallel exchanges inside the persistent tape. `OP_XCHG` writes to uncached peer VRAM over PCIe, publishes an epoch with system-scope release, waits with a timeout for peer data, then adds card 0's partial first on both cards for equal bits. [Exchange source](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/kernels/k3_xchg.h#L1-L13) [Timeout and reduction](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/kernels/k3_xchg.h#L51-L86)
- PyTorch is a runtime dependency in practice even though it is deliberately omitted from package dependency resolution because the PyPI build may be inappropriate. Installation asks for ROCm PyTorch. The bridge uses the HIP library torch already loaded and torch's streams. Buffers, pinned host staging and device transfers use torch APIs; the persistent compute itself launches plain-pointer HIP code objects. Calling the whole engine “PyTorch-free” is false. [Package comment](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/pyproject.toml#L1-L4) [Install instructions](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/README.md#L34-L39) [HIP bridge](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/device/hip.py#L1-L31) [Staging and allocations](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/engine/flashnext_tp.py#L403-L420)
- The build produces gfx1100 HIP code objects ahead of time with compiler/source provenance and packages them as package data. Some kernels compile against the ignite-llama fork's ggml headers; the prefill MMQ is vendored llama.cpp code, instantiated separately by format. [Build provenance](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/build.sh#L1-L61) [Packaged code objects](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/pyproject.toml#L46-L50) [Third-party MMQ scope](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/THIRD_PARTY.md#L11-L32)
- Existing third-party provenance is not “AITER or CK under the hood”: notices identify ggml/llama.cpp, Strata-derived server design, flash-linear-attention-derived dormant training recurrences and transformers-derived templating pieces. This source inspection found no basis to describe AITER as an existing Caminus dependency. [Third-party inventory](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/THIRD_PARTY.md)
- Own-code paths matter: Qwen3-30B-A3B's reader-to-token path excludes llama.cpp code. Its batched prefill directly consumes Q4_K raw blocks and the decode engine's Q6_K planes, using RDNA3 WMMA with fp16 activations and fp32 sums. The dense Qwen35 own-code prefill also uses WMMA and includes its own recurrent-state handoff. [Q3MoE scope](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/qwen3-30b-a3b.md#L1-L10) [Q3MoE prefill](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/q3m.py#L1-L21) [Dense Qwen35 prefill](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/q35own.py#L1-L26)
- Do not repeat the generic architecture page's broad claim that all prefill is bitwise decode. Model-specific q3m/q35own sources explicitly state that WMMA GEMMs are not bitwise decode and use G-model accuracy gates instead. Tests and the relevant engine/prefill code are the authority. [Generic wording](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md#L48-L52) [Q3MoE exception](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/q3m.py#L16-L17) [Qwen35 exception](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/q35own.py#L19-L22)
- The conversation cache owns one live sequence and snapshots recurrent state, convolution/PLE state and selected cache tails, with VRAM/disk tiers and drafter window protocols. Kernel reuse must preserve these state semantics rather than just produce a same-shaped attention output. [Cache source contract](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/cache/prompt.py#L1-L32)
- Numerical change requirements include G-acc versus an fp64 per-op reference, G-model versus the activation reference mode, G-self bitwise across grids and T-token passes, and G-speed in the real shipping module. Speed measurements require interleaved A/B, medians of at least three runs and a 0.05 ms/token threshold. First changed-kernel runs must use the non-display card under the GPU guard. [Own-quant gate definitions](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/specs/spec-own-quant.md#L45-L83) [GPU invariants](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/AGENTS.md#L158-L180)

### Inferences

- The appropriate performance unit for decode is a whole model pass/token at matched model, quantization, context, card placement and drafter settings. An operator that wins in isolation can lose after repacking, activation conversion, synchronization, additional launches, or increased persistent-kernel register pressure. [K3 whole-pass design](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md#L25-L37) [Shipping-module speed requirement](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/specs/spec-own-quant.md#L77-L98)
- Prebuilt gfx1100 objects and controlled provenance are a packaging advantage for the current narrow target, while AITER's broader operator/backend selection offers more design alternatives. Neither observation establishes that one kernel stack is universally faster or easier to maintain. [Caminus build](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/build.sh#L1-L61) [AITER backends/build](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/README.md)

### Gaps

- The existing benchmark documentation establishes results against llama.cpp on particular model/card/settings combinations only. It cannot support a claimed advantage against an AITER-backed engine with a different format, concurrency or architecture. [Benchmark conditions](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/qwen3-30b-a3b.md#L12-L50)
- AITER has layer-level persistent/fused paths, including MegaMoE, per the operator researcher's separate evidence. The report must distinguish these from Caminus's whole-model tape rather than claiming AITER has no persistent kernels or fusion. This note has not independently traced those upstream paths.

## How should Caminus use AITER, and what boundaries matter?

### Takeaway

The most defensible course is to retain K3's whole-model execution contract and evaluate selected RDNA-capable AITER ideas or operators at existing launch seams, especially prefill. Directly adopting a library, porting a kernel into K3, and studying an algorithm are different engineering choices with different costs. [K3 execution contract](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md#L25-L40) [Existing separate prefill launches](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/mmq.py#L28-L46)

### Cited Findings

- Prefill already dispatches separate GEMMs and attention operations over chunks. Its matrix-kernel wrappers consume caller-owned preallocated workspace and explicit layouts. This is an existing seam for substituting a compatible independently launched operator without first dismantling the decode tape. [MMQ wrapper interface](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/mmq.py#L28-L46) [Own prefill structure](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/q35own.py#L1-L26)
- Decode modules enforce operation and weight-format capability lists and refuse unsupported paths before launch. A generic GEMM interface or an operator named “INT4” does not itself satisfy these format/layout contracts. [K3 host capability checks](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/engine/k3.py#L1365-L1383) [Own weight layouts](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/q3m.py#L1-L8)
- AITER's top-level license is MIT, with AMD copyright and a requirement to preserve its copyright/permission notice in copies or substantial portions. Caminus declares AGPL-3.0-or-later and already requires new third-party source to have a retained file-header notice and a THIRD_PARTY.md entry in the same change. This is source-level provenance guidance, not a legal opinion or a statement that every upstream artifact uses the top-level license. [Pinned AITER license](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/LICENSE) [Caminus license declaration](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/pyproject.toml#L9-L16) [Third-party rule](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/THIRD_PARTY.md#L1-L9)
- AITER includes Composable Kernel as a submodule. Any selected source, generated binary, dependency or included submodule needs its own applicable notice/provenance checked; the top-level license should not be assumed to blanket every file or distributed object. [Pinned submodule manifest](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/.gitmodules) [AITER license](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/LICENSE)

### Inferences

- **Keep K3 as the control/execution architecture:** use upstream techniques where they preserve the persistent tape and the supported model's semantics. This retains the latency-oriented design without claiming the present kernels cannot be improved. [K3 design](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md#L25-L40)
- **Try prefill substitutions first:** compare an RDNA-capable AITER attention or GEMM implementation at an existing launch seam, with the exact current cache/weight format or an explicitly costed conversion. Record total prefill time, memory and handoff accuracy, not just the substituted kernel time. The operator researcher should identify specific viable candidates. [Prefill structure](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/q3m.py#L1-L21) [Accuracy gates](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/specs/spec-own-quant.md#L45-L83)
- **For decode, distinguish source port from host call:** a device-body port can fit K3 but must meet the shared register/LDS/task constraints; calling a standalone Python/C++ operator entails additional launch boundaries and scheduling work. It should earn that cost in a complete-pass comparison. [K3 module budget](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md#L27-L35) [Actual launch interface](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/engine/k3.py#L1393-L1414)
- **Treat AITER as a valuable upstream laboratory:** its expanding RDNA support creates useful algorithms, tuning data and test cases. It does not automatically solve the application's prompt-cache policy, recurrent-state reconstruction, conversational retention or rolling-context protocol. Those live in Caminus's engine/cache/session layers. [AITER scope](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/README.md) [Caminus cache contract](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/cache/prompt.py#L1-L32)
- **Avoid a wholesale dependency adoption without a named win:** integrating AITER only because both projects target AMD would add a broader build/backend/runtime surface without demonstrated benefit for current GGUF formats and batch-1 execution. An evidence-based trial names the operator, gfx1100 implementation, layouts, error contract and whole-path benchmark before adoption. [AITER backends/install](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/README.md) [Caminus validation](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/specs/spec-own-quant.md#L45-L83)

### Gaps

- This read-only investigation provides no implementation estimate, measured speedup or license review of a selected kernel/binary. Those require choosing a concrete candidate. The detailed upstream operator notes should narrow that choice.
- No code, kernel objects, installed packages or GPU state were changed or exercised. Only this research-notes file was written.
