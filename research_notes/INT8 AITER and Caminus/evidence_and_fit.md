# INT8 AITER performance evidence and fit

## What does this fork actually claim, and how strong is its evidence?

### Takeaway

This is an actively developed, narrowly targeted downstream MI100 serving stack, with substantially more recent packed-weight work than its README describes. Its measurements support opportunities on that author's gfx908/vLLM configuration; they do not establish a performance advantage on Caminus's gfx1100 pair, formats, persistent scheduling or batch-1 workload. [Pinned fork README](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/README.md) [Fork history](https://github.com/curvedinf/int8-aiter/commits/cd53c11c6d399cd79aee9500536dc5f8206f6ea3)

### Cited Findings

- Snapshot: `curvedinf/int8-aiter` main at `cd53c11c6d399cd79aee9500536dc5f8206f6ea3`, committed November 12, 2026 at 16:29:50 UTC. GitHub metadata identifies it as a fork of `ROCm/aiter`, created June 7, 2026, and not archived. The current history includes regular fork-specific optimization work. [Commit](https://github.com/curvedinf/int8-aiter/commit/cd53c11c6d399cd79aee9500536dc5f8206f6ea3) [Repository metadata](https://api.github.com/repos/curvedinf/int8-aiter)
- README's stated target is **4×MI100, gfx908/CDNA1, TP4, companion curvedinf/int8-vllm, Qwen3.8-27B-class GPTQ W8A8, fp16 serving and DFlash2**. The README explicitly says this is not a general MI100 port and that most inherited upstream operators are not tested on gfx908. This is not a Radeon support fork. [README scope](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/README.md)
- The README reports CK A8W8 GEMM **1.8× at M=64 to 6.8× at M=8** versus a vLLM Triton W8A8 packed-GPTQ baseline, and approximately **1.8e-4 mean relative kernel error**. These are author-reported operator comparisons, not model throughput results. The linked verification script contains no timing code or implementation of that performance baseline. [README claim](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/README.md) [Actual linked test](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_gemm_a8w8_int8_gfx908.py)
- That CK test uses seeded Gaussian X/W, per-token INT8 quantization, M in 1/8/64/512/4096 and projections `(K,N)` of `(5120,5120)`, `(5120,17408)` and `(17408,5120)`. Its reference multiplies the **already quantized then dequantized** X/W, so it measures the GEMM implementation after quantization, not total error against the original model. It prints mean relative error with denominator clamped at 1e-2 and counts failures below a 1e-3 threshold, but has no assertion or nonzero failure exit. [Test source](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_gemm_a8w8_int8_gfx908.py)
- Separate fork benchmarks distinguish eager launch overhead from graph-captured kernel time. Eager timing uses 20 warmups and averages 1000 iterations for M=1 or 300 otherwise with GPU events. Graph timing captures 100 independent GEMMs, warms five eager calls and three replays, then averages 20 graph replays divided by 100. These are useful microbenchmarks, but not interleaved A/B process medians or a complete serving workload, and they compare default-versus-tuned CK settings rather than reproducing README's packed-GPTQ baseline. [Eager benchmark](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/tuning_tests/bench_default_vs_tuned_gfx908.py) [Graph benchmark](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/tuning_tests/bench_graph_default_vs_tuned_gfx908.py)

This is not reported as a complete model token/s speedup. Current source sets `BM=16` for M≤128, but the actual warp/stage selection also depends on M; quote measured configuration and source separately. This is stronger evidence than a synthetic GEMM ratio, but still the author's paired vLLM deployment, not our measurement. ### Inferences

- This fork's strongest evidence is candid, workload-specific engineering: component measurements, real-state comparisons, graph-replay tests, serving trials and reversions when aggregate results disappoint. The right interpretation is “potentially useful work to study and reproduce,” not “established universal acceleration.” [Cache experiment and revert](https://github.com/curvedinf/int8-aiter/commit/15a3e419553d970169edbf386a4ff7166dcc2f2a) [Five-run later result](https://github.com/curvedinf/int8-aiter/commit/dc13c3d1895e6bd6973f5dcf24049d5d9e66751e)
- Kernel speed, milliseconds per speculative step, acceptance and delivered tokens/s are different metrics. Concurrency magnifies this distinction: a batch containing multiple requests and verify positions is not Caminus's single live sequence. [Measured attention tradeoff](https://github.com/curvedinf/int8-aiter/commit/2d5f5e0b55325f0799538550b2a63722092deac5) [Caminus worker](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/serve/worker.py#L1-L14)

## What accuracy, state and maturity boundaries matter?

### Takeaway

The fork has valuable correctness work, particularly exact parity for its own cached-versus-packed paths and captured refresh. Those tests do not prove bitwise preservation of original GGUF arithmetic or model-level quality. Recent native attention and GEMM experiments remain explicitly gated, and the newest source additions have Apache-2.0 notices despite the top-level MIT license. [Cache tests](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_packed_expert_cache_gfx908.py) [Native gates](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/int8_native.py)

### Cited Findings

- The fork has newer packed codecs, not just INT8 checkpoints: current dense tests cover **NVFP4, IQ2_XXS and Q8_0**, with partial slices and different batch sizes. Expert caches retain packed IQ2 originals for misses and expand admitted experts into INT8 GS128 copies. Static dense promotion can release original packed source references. These are **packed-storage plus INT8 execution** strategies; calling every weight originally INT8 misses the newer design. [Dense cache tests](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_packed_dense_cache_gfx908.py) [Expert cache design](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/packed_expert_cache.py) [Ownership change](https://github.com/curvedinf/int8-aiter/commit/3b85a215019c3218a82e782929a268e03a333bb4)
- The cache tests check exact output equality against the fork's existing packed path, not original floating-point model weights. Tests cover hits/misses, replacement, real versus padded expert IDs, stable slot retention, partial TP boundaries, graph replay with changed routes, pointer stability, memory budget and no reallocation during prefill. The newer test files use pytest assertions and skip explicitly outside gfx908, unlike the older print-only CK test. [Expert tests](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_packed_expert_cache_gfx908.py) [Prefill tests](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_packed_prefill_gfx908.py) [Dense tests](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_packed_dense_cache_gfx908.py)
- Both dense and expert cache modules default their local `VLLM_BOLT_*_CACHE_GIB` budget to zero. A companion engine can override the environment, so these module defaults do not by themselves describe every deployed recipe. [Dense budget](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/packed_dense_cache.py) [Expert budget](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/packed_expert_cache.py)
- Native primitive self-tests check integer MFMA lane maps, LDS loading and token reduction bit-exactly versus torch. The actual native helper assumes a 64-lane wave and `v_mfma_i32_16x16x16i8`; these are gfx908 implementation contracts, not portable gfx1100 kernels. Its site gates default off via `AITER_INT8_NATIVE=0`. [Native helper](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/csrc/kernels/int8_mfma_lane.cuh) [Loader/self-tests/gates](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/int8_native.py)
- November 11 native attention microbenchmarks report 1.54× at 16K and 1.14× at 2K for 12 sequences × 8 queries, before later serving checks. Subsequent history records a failed serving gate despite synthetic references passing, then identifies a comparison-harness mutation bug and reports offline agreement within 1.6e-2 on a dumped real call. The final note reports 60.1–61.0 ms/step native versus 65.3–68.1 Triton, but acceptance 1.53 versus 1.71–2.09, so native stays opt-in. The old failed gate alone is stale; the final acceptance tradeoff remains material. [Initial operator results](https://github.com/curvedinf/int8-aiter/commit/bd73f09a6a315551f0509a61d3250762df8fbca7) [Failed gate](https://github.com/curvedinf/int8-aiter/commit/0cfc9a99426b1e2057edc0cd90969d25a941e73c) [Subsequent diagnosis and final status](https://github.com/curvedinf/int8-aiter/commit/2d5f5e0b55325f0799538550b2a63722092deac5)
- The same final note says Hadamard KV rotation collapsed DFlash2 acceptance to 1.0 in both arms because the draft KV-injection path did not carry the rotation. Rotation was switched default-off until consistent. This is particularly relevant to Caminus, whose drafters consume target features and own cache state; a numerically appealing target-only transform can damage the full speculative path. [Rotation/acceptance diagnosis](https://github.com/curvedinf/int8-aiter/commit/2d5f5e0b55325f0799538550b2a63722092deac5)
- Native small-M GS128 GEMM experiments explicitly remain unwired after missing speed gates. November 12 history records initial 1.4–2.4× slower than Triton, then split-K variants 17–76% behind; the latest multi-wave revision is close at M16 but 57% behind at M96. Treat implementation presence as experimental code, not a production improvement. [Initial native GEMM](https://github.com/curvedinf/int8-aiter/commit/2dbb5be4ee879a1fad091df258493fb459a19af8) [Split-K experiment](https://github.com/curvedinf/int8-aiter/commit/a00b0a501a6a1a522814aa1beb9f8ed9a9b3a62f) [Latest revision](https://github.com/curvedinf/int8-aiter/commit/2c4c312323e397cee08cb80284a31dab0a6c1ac4)
- Some October 15 packed-kernel commits explicitly say full fidelity evaluation was deferred and coherence smoke passed. Later component/real-checkpoint cache parity improves confidence in equivalent fork paths, but does not retroactively establish a model-quality gate against the original checkpoint for every transformation. [Example limited validation](https://github.com/curvedinf/int8-aiter/commit/4c578a556dadfbbfb72a4d3239b5f1b0b9b835a4) [Later parity claim](https://github.com/curvedinf/int8-aiter/commit/dc13c3d1895e6bd6973f5dcf24049d5d9e66751e)
- Fork top-level LICENSE retains the upstream MIT blob, but new packed cache modules, native loader and gfx908 lane primitives have **SPDX Apache-2.0**, with the lane helper also naming contributors to the int8-vllm project. Reusing those additions requires their actual notices/provenance, not a blanket “AITER is MIT” assumption. This is a source observation, not a legal review. ### Inferences

- Exact cache-vs-packed parity demonstrates a representation-cache optimization preserves the fork's own arithmetic. It does not make low-bit→GS128 INT8 conversion lossless relative to Caminus's exact weight decode or original checkpoint, and it does not satisfy Caminus's G-acc/G-model gates without additional evaluation. [Fork parity tests](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_packed_dense_cache_gfx908.py) [Caminus quant gates](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/specs/spec-own-quant.md#L45-L98)
- A smaller milliseconds-per-step number cannot establish faster speculative output if acceptance falls. The full pipeline must count accepted tokens, include draft/injection costs and verify output/quality on the same trajectory. The fork's decision to keep the path opt-in is a useful example of this distinction. [Serving measurement and status](https://github.com/curvedinf/int8-aiter/commit/2d5f5e0b55325f0799538550b2a63722092deac5)

### Gaps

- README mentions an end-to-end KLD boot check in the companion fork, but this bounded inspection did not establish its current thresholds, calibration prompts or measured KLD for each new packed path. Do not imply equivalence to Caminus's documented quality gates. [README validation statement](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/README.md)
- Searching ROCm/aiter PRs for author curvedinf returned no results during this investigation. That is not proof no patches or ideas were upstreamed under other authors; no upstream maintainer endorsement of these specific additions was established.

## Does it change the recommendation for Caminus?

### Takeaway

It strengthens the case for studying **specific representation, fusion, routing and cache techniques**, rather than adopting a monolithic replacement backend. It adds a relevant low-bit-to-INT8 design branch that the original AITER comparison did not explore, but the current implementation's gfx908/native assumptions, codec gaps, accuracy cost and extra memory prevent treating it as a direct Radeon upgrade. [Packed cache strategy](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/packed_expert_cache.py) [Native hardware assumptions](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/csrc/kernels/int8_mfma_lane.cuh)

### Cited Findings

- The native packed loader compiles explicitly with `--offload-arch=gfx908` and loads the resulting shared library. A generic Triton wrapper does not make calling this path Radeon-safe. RDNA3 would need its own compatible dispatch/implementation; changing a compiler architecture flag does not translate MFMA fragment layouts. [Native packed loader](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/gemm_packed_native.py) [Lane assumptions](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/csrc/kernels/int8_mfma_lane.cuh)
- Resident caches spend additional INT8 payload capacity to avoid repeated low-bit decoding. Expert caches retain packed originals for misses, while static dense promotion changes ownership. Caminus checks every allocation against per-card capacity and keeps 512 MiB free on the display card, so a multi-GiB expert cache cannot be assumed affordable on its 24/20 GB pair. [Cache ownership design](https://github.com/curvedinf/int8-aiter/commit/3b85a215019c3218a82e782929a268e03a333bb4) [Caminus allocation invariants](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/AGENTS.md#L158-L180)
- Caminus's Qwen3-30B-A3B prefill consumes raw Q4_K and Q6_K planes, with fp16 activation WMMA and model gates. Fork tests establish other codecs and a GS128 INT8 arithmetic contract; neither matching “quantized model” labels nor similar byte widths prove compatibility. The operator researcher's notes provide the precise codec/rounding differences. [Caminus prefill contract](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/q3m.py#L1-L21) [Fork codec tests](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_packed_dense_cache_gfx908.py)

### Inferences

- **Most useful fork-specific investigation:** borrow the bounded **hot-expert cache policy**, rather than its MI100 kernels. Measure whether repeated expert decoding during a real Caminus prefill is a bottleneck, and whether a small capacity-projected cache for the actual served format pays after admission/refresh/misses and extra weight traffic. Evaluate first at a separate prefill launch boundary on the non-display XT. Preserve a packed fallback and stable ownership; do not start by expanding an entire model. This is a proposed experiment, not an established speedup or an implementation-ready drop-in. [Measured resident-prefill result](https://github.com/curvedinf/int8-aiter/commit/dc13c3d1895e6bd6973f5dcf24049d5d9e66751e) [Cache policy/tests](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_packed_expert_cache_gfx908.py) [Caminus prefill seam](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/mmq.py#L28-L46)
- **Keep the existing direct-operator shortlist:** compatible upstream gfx1100 attention or already-FP16/BF16 projection prefill remains simpler than first adding new packed codecs, GS128 requantization and MI100-native kernels. The fork changes the design ideas worth considering, not the basic recommendation to preserve K3 and test one named seam at a time. [Prior report](../../reports/AITER%20and%20Caminus%20compared.md) [Caminus prefill and accuracy contract](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/q35own.py#L1-L26)
- **Retain K3 for current decode until a complete-pass win exists:** standalone graph-captured vLLM kernels and library caches cannot be inserted into a whole-model persistent tape without adapting scheduling, scratch, register budgets and state ownership. INT8 conversion can reduce ALU cost while increasing bytes read relative to 2–4-bit weights; at batch 1 the tradeoff is especially workload-dependent. Evaluate with original checkpoints, matched context, drafter acceptance and Caminus's own error/speed gates. [K3 contract](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md#L25-L40) [Caminus gates](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/specs/spec-own-quant.md#L45-L98)
- **Carry over lessons, not measurements:** precise scale layout contracts, captured-buffer lifetime, padded expert exclusion, bounded caches and measuring rejection/acceptance effects apply directly to engineering practice in Caminus. None requires copying a gfx908-specific kernel or adopting the companion serving engine. [CK scale contract](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_gemm_a8w8_int8_gfx908.py) [Graph/cache tests](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_packed_expert_cache_gfx908.py) [Acceptance lesson](https://github.com/curvedinf/int8-aiter/commit/2d5f5e0b55325f0799538550b2a63722092deac5)

### Gaps

- No concrete operator in this fork has been established here as immediately runnable, compatible and faster for the actual mixed gfx1100 pair. The next engineering step is a bounded compatibility experiment, not deployment.
- The proposed hot-expert study needs real route reuse, actual headroom and prefill profiles before choosing an implementation. Zero spare memory or insufficient route locality would reject it before kernel work.
- No builds, installs, source changes or GPU execution were performed. This notes file is the sole output written for this assignment.
