# INT8 AITER and Caminus

**This fork is more relevant to Caminus's low-bit model work than its name or README first suggests, but its new native kernels target MI100, not your Radeon cards.** It goes beyond ordinary W8A8 GEMM: current source decodes selected packed GGUF formats, executes group-scaled INT8 math, and caches expanded hot experts while retaining compressed originals. Those are useful design comparisons for Caminus. They are not a direct backend upgrade: the hardware instructions, quantization, cache layouts and serving execution differ. For immediately usable Radeon operators, upstream AITER's experimental gfx1100 paths remain the better starting point; this fork mainly adds techniques worth studying or porting. ([Packed interfaces](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/gemm_packed_g128.py#L89-L148), [Native target](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/gemm_packed_native.py#L17-L52), [Upstream hardware](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/README.md#supported-hardware))

Research date: **November 12, 2026**. Fork snapshot: [`cd53c11c6d399cd79aee9500536dc5f8206f6ea3`](https://github.com/curvedinf/int8-aiter/commit/cd53c11c6d399cd79aee9500536dc5f8206f6ea3). Comparison baselines are upstream AITER `37da1dbeb305e868dda2e52d0d084a30fd71a99c` and Caminus `25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62`, as in the [earlier report](<AITER and Caminus compared.md>). No installations, builds or GPU runs were performed.

## The fork specializes a real MI100 serving stack

The declared deployment is four MI100s, gfx908/CDNA1, TP4, Qwen3.8-27B-class models, DFlash2 and graph-captured execution through the companion `curvedinf/int8-vllm`. The initial path uses W8A8: weights and activations both become INT8 operands, with floating-point scales. The project explicitly limits its MI100 claims rather than promising that every inherited AITER operator works there. ([Fork intent](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/README.md#serving-stack-this-fork-targets))

That specialization resembles Caminus's approach of optimizing a concrete quantized speculative workload. The surrounding engine still comes from vLLM, however; the fork does not implement Caminus's whole-model persistent tape, prompt-cache contract or complete service within AITER itself. ([Fork integration](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/README.md), [K3 organization](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md#L25-L40))

| Dimension | Upstream AITER | INT8 fork additions | Caminus implication |
|---|---|---|---|
| Primary scope | Broad AMD operator ecosystem | Specific MI100 serving optimization | Useful specialist comparison, not a replacement engine |
| Hardware | Experimental gfx1100 paths among many targets | New native gfx908 MFMA implementations | Native additions require an RDNA port |
| Low-bit storage | Several integer/floating quantization families | Actual IQ2_XXS, Q8_0 and NVFP4 packed codecs | More concrete GGUF overlap, still incomplete catalog coverage |
| Computation | Operator-specific precision | Packed weights requantized to grouped INT8 | New math requires accuracy gates |
| Weight caching | Broader backend machinery | Bounded expanded dense/expert representations | Potential decode-cost versus memory tradeoff |
| Integration | Framework-selected operators | Companion vLLM adapters and captured state | K3 scheduling and ownership remain separate work |

The README understates current implementation. It describes roughly 16 changed files and build work as planned, while an implemented gfx908 build profile and tuning rows exist. Against the verified August 21 upstream parent `03624e356efb57a72c88776e2adc04ca31ca404c`, the pinned fork has **89 additional commits and 96 changed files**. Those counts are not its ahead/behind relationship to current upstream main: the current cross-repository comparison could not be established. Source and dated history are stronger evidence than the stale build-plan description. ([Known-parent comparison](https://github.com/curvedinf/int8-aiter/compare/03624e356efb57a72c88776e2adc04ca31ca404c...cd53c11c6d399cd79aee9500536dc5f8206f6ea3), [Implemented profile](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/setup.py#L267-L298), [Tuning inventory](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/configs/a8w8_tuned_gemm.csv))

## Packed GGUF support changes the arithmetic

The newer packed path supports **IQ2_XXS, Q8_0 and NVFP4**. IQ2_XXS includes real codebook/sign decoding; this is not simply a kernel accepting an already expanded INT8 matrix. But the inspected codec dispatch does not provide Q4_K, Q6_K or the other IQ families used across Caminus. IQ2_XXS is also distinct from IQ2_S. The presence of one IQ codec cannot establish compatibility with all low-bit GGUF models. ([Codec dispatch and geometry](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/gemm_packed_g128.py#L89-L148), [Actual packed decoders](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/_triton_kernels/gemm/basic/gemm_packed_g128.py#L9-L43), [Caminus formats](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/engine/k3.py))

Its central trade is **compressed storage with INT8 execution**. For each 128-element activation group, it finds a scale and rounds values to signed INT8. It decodes and separately requantizes weights into INT8 groups, computes an INT32 dot product, then applies activation/weight scales and accumulates groups in FP32. Cached weights reuse the same quantized values and scales. This is not lossless repacking: both operand quantization and reduction behavior change. Even Q8_0's independent 32-value scales become a different 128-value scaling contract. ([Activation quantization](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/_triton_kernels/gemm/basic/gemm_packed_g128.py#L82-L89), [Weight conversion and accumulation](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/_triton_kernels/gemm/basic/gemm_packed_g128.py#L159-L192))

The cache is the most interesting engineering consequence. It admits selected experts into expanded INT8 slots, preserves surviving slots and retains packed originals for misses. Dense weights can instead transfer ownership to an immutable expanded copy and release their packed source references. Both local cache budgets default to zero unless deployment settings enable them. Tests cover cache parity, replacement, partial TP boundaries, changed routes under graph replay and pointer stability. That establishes transparency within the fork's own arithmetic; it does not prove equivalence to original GGUF math. ([Expert policy](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/packed_expert_cache.py#L299-L347), [Dense ownership](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/packed_dense_cache.py#L95-L132), [Cache tests](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_packed_expert_cache_gfx908.py))

The memory cost is material for a 24/20 GB machine. One INT8 value per weight plus one FP32 scale per 128 weights gives **1.03125 bytes/weight**. Derived from the block sizes, that expanded representation is about 1.83× Q4_K, 1.26× Q6_K, 4× IQ2_XXS and 3.22× IQ2_S, before metadata. An expert cache adds the expanded payload while retaining the packed original. These are representation calculations, not measured allocations. At batch-one decode, extra weight traffic can outweigh cheaper arithmetic; prefill has more reuse over tokens and can amortize conversion differently. ([Expanded layout](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/packed_dense_cache.py#L146-L161), [Caminus block sizes](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/engine/k3.py))

Producer fusion is another transferable idea. The fork combines projection/SiLU or SwiGLU with output quantization, avoiding an intermediate activation write and a separate quantizer. Some producer GEMMs remain floating-point and merely emit an INT8 output, so “everything uses integer multiplication” would be inaccurate. Caminus could study this fusion pattern while retaining its own consumer format and rounding contract. ([Fused SiLU/output quantization](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/gemm_silu_quant_out.py), [Floating projection variant](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/gemm_float_quant_out.py))

## Native MI100 kernels need more than an architecture flag

The native helper directly uses `v_mfma_i32_16x16x16i8` with documented wave64/CDNA lane mappings. This is genuine MI100 INT8 matrix arithmetic, rather than software FP8 emulation. It is also a different instruction/layout contract from Caminus's RDNA3 WMMA paths. Changing `gfx908` to `gfx1100` does not translate fragments, synchronization or instruction selection. ([MFMA primitive](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/csrc/kernels/int8_mfma_lane.cuh#L4-L61), [Native GEMM contract](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/csrc/kernels/gemm_a8w8_m16_gfx908.hip#L4-L17))

There is a concrete dispatch caveat: the packed loader hardcodes `--offload-arch=gfx908`, while eligible small-M dispatch checks shapes and epilogues without checking the actual GPU architecture. A generic Python/Triton wrapper therefore does not guarantee a Radeon-safe fallback. The separate CK gate correctly rejects gfx11/gfx12 for its CDNA objects, but that guard cannot be assumed to protect every newer path. A candidate must be traced to its final implementation before any local run. ([Packed loader](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/gemm_packed_native.py#L17-L52), [Shape-based selection](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/gemm_packed_g128.py#L173-L209), [CK architecture gate](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/gemm_op_a8w8.py#L54-L60))

The native INT8 attention path is a separate approximation experiment. It uses per-token/head INT8 KV, quantizes Q, and requantizes probabilities before the integer PV multiplication, with FP32 softmax statistics and BF16 output. Its representation differs from Caminus's Q8_0 cache. Faster integer attention therefore needs its own quality and speculative-acceptance evidence, rather than being treated as a transparent cache-format swap. ([Attention math](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/csrc/kernels/paged_attn_decode_int8_pthead_gfx908.hip#L4-L19), [Probability quantization](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/csrc/kernels/paged_attn_decode_int8_pthead_gfx908.hip#L282-L333))

## Measurements support experiments rather than adoption

The fork has substantive tests and candid reversions, but its results belong to the author's MI100/vLLM stack. The README's 1.8–6.8× CK GEMM claim compares specific matrix shapes against a packed-GPTQ baseline. Its linked correctness test has no timing implementation of that baseline, measures already-quantized operands, and prints failures without a failing assertion/exit. Newer cache tests use assertions and real-checkpoint comparisons, offering stronger evidence for their narrower contracts. ([README measurement](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/README.md), [Original CK test](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_gemm_a8w8_int8_gfx908.py), [Newer dense tests](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/op_tests/test_packed_dense_cache_gfx908.py))

| Author-reported result | What it supports | Limit |
|---|---|---|
| Resident-expert prefill: +14.4% prefill, +2.6% decode, five-run medians, 1024 input/256 output, C6 | Expanded expert caching can pay in one real deployment | C means concurrency; not Caminus's single sequence or context size |
| Latest fused SiLU component: roughly 143–334 µs to 53–68 µs at M96 | Small-batch tile occupancy matters | One component/shape; not a complete token-rate improvement |
| Native attention: lower milliseconds/step but lower acceptance | Kernel latency alone is insufficient for speculative decoding | Delivered token rate and quality need the full pipeline |

These measurements come from the resident-prefill and latest geometry commits. Earlier cache-prefill work was reverted after a decode recheck and later reintroduced; its gains must not be stacked with current results. ([Resident result](https://github.com/curvedinf/int8-aiter/commit/dc13c3d1895e6bd6973f5dcf24049d5d9e66751e), [Latest component tuning](https://github.com/curvedinf/int8-aiter/commit/cd53c11c6d399cd79aee9500536dc5f8206f6ea3), [Earlier revert](https://github.com/curvedinf/int8-aiter/commit/15a3e419553d970169edbf386a4ff7166dcc2f2a))

Historical end-to-end evidence is mixed in a useful way. A June companion-engine attention report, using a different model/MTP configuration, found gains at some long-context/concurrency settings but a 10.2% regression for a short 512-input/256-output C16 workload; without MTP it reported approximately a tie. That report is not current DFlash evidence. It reinforces the need to match model, context, concurrency and speculative settings instead of transferring a kernel ratio to engine speed. ([Historical serving evaluation](https://github.com/curvedinf/int8-vllm/blob/73a386c8fa8539d167a529718b3c4dacbf5e5ea8/docs/mi100_decode_opt/ua_eval_dense27b_gfx908.md))

The latest attention diagnosis matters more than the initial failed gate alone. A comparison-harness mutation bug was identified, and the follow-up reports offline agreement on a real dumped call. Nevertheless, native serving measured roughly 60–61 ms/step versus 65–68 ms for Triton while acceptance fell to 1.53 versus 1.71–2.09, leaving native opt-in. Hadamard KV rotation separately collapsed DFlash2 acceptance because the injection path lacked the transform; rotation remains default-off. This is directly relevant to Caminus: target, drafter and injected state must agree on representation. ([Follow-up diagnosis and status](https://github.com/curvedinf/int8-aiter/commit/2d5f5e0b55325f0799538550b2a63722092deac5))

Native code presence also does not mean a selected production improvement. The newer standalone small-M GS128 GEMM experiments remained unwired after missing speed gates; the latest multi-wave revision approached the reference at M16 but remained 57% behind at M96. Those experimental kernels must be distinguished from already dispatched packed kernels and from the accepted fused-output tuning. ([Latest experimental GEMM result](https://github.com/curvedinf/int8-aiter/commit/2c4c312323e397cee08cb80284a31dab0a6c1ac4))

My proposed priority is **measure route reuse and prefill decoding cost before implementing a hot-expert cache**. Reject it early if headroom or locality is insufficient. Next study producer/quantizer fusion and codec lookup/value-decoding strategies for the formats Caminus actually serves. Only then consider an isolated matching-format grouped-INT8 prefill port with explicit RDNA dispatch. Native INT8 attention should remain a separate quality experiment. None justifies expanding the entire catalog or replacing K3. ([Cache strategy](https://github.com/curvedinf/int8-aiter/blob/cd53c11c6d399cd79aee9500536dc5f8206f6ea3/aiter/ops/triton/gemm/basic/packed_expert_cache.py), [Prefill boundary](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/mmq.py#L28-L46))

Any changed quantized math must pass Caminus's per-op accuracy, model-quality, self-consistency and complete-module speed gates. Cache parity within the fork is not a substitute. A whole-pass comparison must include conversion, cache maintenance, memory traffic, draft/injection cost and accepted tokens. Weight caches also do not implement the rolling conversation context discussed earlier: they cache model representations, not conversation history. ([Caminus numerical gates](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/specs/spec-own-quant.md#L45-L98), [Conversation-state contract](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/cache/prompt.py#L1-L32))

Finally, the repository's MIT license does not describe every addition: newer native helpers/loaders and packed cache modules carry Apache-2.0 notices. A selected port needs its actual per-file/dependency notices preserved and a Caminus third-party inventory entry. No license review of a concrete integration was performed.
