# AITER and Caminus compared

**Caminus is a complete, hardware-specialized inference engine; AITER is an overlapping library of AMD operators and execution techniques.** AITER could improve selected parts of Caminus, but it does not replace K3, model loading, conversation state, checkpointing or the API server. Its current experimental gfx1100 support makes it relevant to the RX 7900 cards, rather than something to dismiss as Instinct-only. Its persistent MoE and recurrent-model work also overlaps Caminus more closely than a conventional GEMM library would. The strongest initial opportunities are selected prefill operations and algorithm comparisons; replacing the whole decode path has much higher integration costs. **No matched benchmark currently establishes that either stack is faster for Caminus's workload.** These conclusions come from source inspection, not installation or GPU execution. ([AITER scope and hardware](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/README.md), [Caminus architecture](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md))

Research date: **November 12, 2026**. AITER is pinned to [`37da1dbeb305e868dda2e52d0d084a30fd71a99c`](https://github.com/ROCm/aiter/commit/37da1dbeb305e868dda2e52d0d084a30fd71a99c), committed that day. Caminus is compared at local HEAD [`25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62`](https://github.com/jdominick05/caminus/commit/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62). Current code takes precedence over older issue reports and broad documentation claims.

## Caminus owns the engine around the kernels

AITER supplies reusable operations through several implementation families: HIP, Triton/Gluon, Composable Kernel, assembly, FlyDSL and OPUS. Larger frameworks choose and integrate those implementations. Its ecosystem includes vLLM and SGLang integration; the distinction between AITER and ROCm's ATOM engine is useful here: an engine built with AITER still needs an engine. Caminus already supplies that surrounding system and its own compute implementation. ([AITER introduction and ecosystem](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/README.md), [OPUS design](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/csrc/include/opus/README.md))

| Dimension | Caminus today | AITER today | Practical meaning |
|---|---|---|---|
| Product layer | Model loading, decode/prefill, cache, drafters and HTTP service | Operators, fused kernels and supporting integration machinery | The kernel layer overlaps; the complete products are different |
| Hardware focus | Directly tested RX 7900 XTX + XT, gfx1100 | Broad AMD coverage with backend-specific targets; gfx1100 experimental | Compare the selected path on the actual cards |
| Serving workload | One live sequence, batch 1, FIFO request execution | Building blocks used by frameworks with different scheduling policies | Multi-user throughput is an engine-level comparison |
| Decode scheduling | Whole-model persistent task tape per participating GPU | Standalone, fused and some persistent layer implementations | Neither “all per-op launches” nor “the same megakernel” is accurate |
| Weight representation | GGUF formats and model-specific packed layouts | Several floating-point and integer quantization families | A matching bit count does not imply compatible weights |
| Runtime | PyTorch allocations/streams plus direct HIP compute launches | Ordinary Python path imports PyTorch; other interfaces exist | “PyTorch-free versus PyTorch” misdescribes the distinction |
| State ownership | Live token log, recurrent state, cache checkpoints and disk parking | Operator inputs/outputs and state primitives | Application retention and recovery remain Caminus responsibilities |

The workload distinction is explicit in Caminus's worker: it processes one live sequence at a time. Multiple accepted HTTP connections or parked conversations do not imply continuous batching of active sequences. Its architecture registry and catalog cover selected Qwen families and derivatives, rather than arbitrary models. That narrow scope enables specialization, but also limits what its existing benchmark results establish. ([Worker contract](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/serve/worker.py#L1-L14), [Model catalog](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/models.py#L82-L102))

K3 represents the operations across a decode or verify pass as a persistent tape. Workgroups claim dependent tasks and synchronize through bounded waits. For two cards, each participating GPU runs its target kernel; this does not mean one launch covers an entire HTTP request, including prefill, drafting and recovery. Operations share a register allocation, so an apparently useful addition can slow unrelated tasks through register pressure. The documented budget is 96 VGPRs with no VGPR spills. ([K3 execution and modules](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/dev/architecture.md#L25-L40), [Actual launch path](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/engine/k3.py#L1393-L1426))

Both projects use framework runtime resources. Caminus uses PyTorch for tensors, allocations, pinned staging and streams, then launches its HIP code objects with plain pointers. AITER's normal Python entrypoint imports torch; its JIT also caches imported extension modules and supports prebuilds. **Cold compilation is a startup concern, not a compilation cost on every token.** Any comparison must separate installation, first-use compilation, warmed dispatch and actual GPU execution. ([Caminus HIP bridge](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/device/hip.py#L1-L31), [AITER entrypoint](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/__init__.py#L1-L8), [AITER module cache](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/jit/core.py#L1143-L1153), [Prebuild handling](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/setup.py#L298))

## Experimental RDNA3 support is real and selective

The pinned README explicitly lists the Pro W7900, gfx1100, as experimental. It describes Triton, most FlyDSL and most HIP paths as RDNA-capable, while most CK/assembly paths remain CDNA-only. This is relevant architecture support, but it does not qualify every operator on Caminus's exact XTX/XT combination. ([Hardware table](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/README.md#supported-hardware))

Source confirms intentional gfx1100 work. The core build allow-list accepts it, and current tuning directories contain attention and GEMM configurations. However, another compilation helper still excludes gfx1100, and OPUS GEMM's architecture dispatch recognizes gfx942, gfx950 and gfx1250 while identifying gfx1100 as future work. A successful package import or broad architecture gate therefore proves less than checking the precise entrypoint. ([Core allow-list](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/jit/core.py#L960-L995), [gfx1100 configurations](https://github.com/ROCm/aiter/tree/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/configs/gfx1100), [Separate helper](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/csrc/cpp_itfs/utils.py#L230-L253), [OPUS dispatch](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/csrc/opus_gemm/include/opus_gemm_arch.cuh#L13-L57))

The hardware instruction differences matter most for low precision. AITER classifies gfx1100 FP8 as software-emulated: values are converted to FP16 and multiplied through FP16 WMMA. Native Instinct FP8/FP4 speed claims cannot be transferred to this path. Its target utilities also include a 96-CU gfx1100 configuration associated with the XTX, which is not proof of equally complete tuning for the 84-CU XT. The inspected main CI workflow primarily exercises MI300/MI35X hardware, without an RDNA runner in that workflow. ([Capability predicates](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/utils/_triton/arch_info.py#L30-L79), [CU mappings](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/jit/utils/build_targets.py#L33-L92), [CI matrix](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/.github/workflows/aiter-test.yaml#L540-L557))

Recent integration work makes older dismissals stale. vLLM PR #52970 merged on October 27, 2026, enabling AITER Triton RDNA3 paths, including attention and GDN-related support. A subsequent maintainer explanation says RDNA needs its separate gate because the global AITER gate also enables unsupported CK and assembly paths. That is a more useful compatibility model than treating AITER as one all-or-nothing switch. ([Merged vLLM change](https://github.com/vllm-project/vllm/pull/52970), [Maintainer clarification](https://github.com/ROCm/aiter/issues/4604#issuecomment-6539644216))

Issue #6574 supplies actual RX 7900 XT user reports: several KDA, attention, topk and normalization tests passed, while other operations had import/configuration problems and an emulated-FP8 GEMM reportedly hung. Those tests used an older AITER commit. Some missing configurations now exist, so the report cannot establish that those exact defects persist; neither does current config presence prove the hang fixed. These are upstream observations, not tests conducted here. ([Dated test report](https://github.com/ROCm/aiter/issues/6574), [Current GEMM default](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/configs/gfx1100/triton/gemm/gemm_a16w16/DEFAULT.json))

## Operator overlap does not imply compatible formats

**The nearest overlap is attention/QSA and hybrid-model state computation.** AITER QSA has compressed-key scoring, selection expansion with a causal tail, and sparse paged grouped-query attention. Four-token compression matches an important structural feature of Caminus's indexer. However, AITER's inspected paths use unquantized, FP8 or MXFP4 compressed keys and unquantized/FP8 KV; Caminus's Q8_0 blocks and K3 traversal are different representations. This makes QSA a strong algorithm/reference candidate, with conversion and numerical work required before direct use. ([AITER QSA interfaces](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/attention/qsa.py#L273-L305), [Sparse GQA formats](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/attention/qsa.py#L529-L616), [Caminus QSA implementation](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/engine/flashnext_tp.py))

Low-bit naming requires particular care. AITER's generic `gemm_a16w4` explicitly supports gfx1100 and represents groupwise unsigned INT4 with integer zero points and scales, including GPTQ/AWQ adapters. Its MoE `a16w4` instead means MXFP4, with E2M1 values and E8M0 scales. Neither interface decodes Caminus's GGUF Q4_K/Q6_K blocks or IQ codebooks. Lossless repacking is distinct from requantizing existing values into a new scheme; the latter changes the model and its accuracy contract. Expanding all weights to FP16 would also abandon the memory assumptions that make the current catalog fit. ([Generic INT4 equation](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/gemm/basic/gemm_a16w4.py#L20-L62), [MoE MXFP4 contract](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/moe/moe_op_gemm_a16w4.py#L338-L430), [Caminus format-specific prefill](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/q3m.py#L1-L21))

AITER also has generic recurrent and chunked Gated DeltaNet APIs. Chunk algorithms can expose more prefill parallelism, but state layout, precision and accumulation order determine whether they preserve Caminus's handoff and verification behavior. The specialized fused Qwen3-Next GDN implementation is explicitly gfx950-only. Its documentation distinguishes GDN from KDA, so an RDNA KDA success does not establish that the fused Qwen GDN path works there. The HIP chunk-state wrapper adds its own BF16 and fixed-chunk constraints. ([Generic GDN](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/gated_delta_net/gated_delta_rule.py#L39-L58), [Chunk-state contract](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/chunk_gated_delta_rule_fwd_h.py#L200-L251), [Fused GDN constraints](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/gated_delta_net/fused_gdn_decode_qkvz.py#L4-L28))

| Area | Relevant AITER capability | Main Caminus integration obligation |
|---|---|---|
| Dense attention | Paged KV, unified attention, split-KV dispatch | Cache layout, masks, output precision and existing numerical gates |
| QSA | Compressed scoring, selected token expansion, sparse GQA | Q8_0 representation, tie rules, causal tails and K3 scheduling |
| GDN/convolution | Recurrent/chunked rules and stateful causal conv | Head topology, recurrence order, lazy commit and checkpoint state |
| Quantized GEMM/MoE | Multiple INT4, FP8 and FP4 families | Exact weight representation, scales and conversion capacity |
| Norm/RoPE | Fused normalization, rotation and cache writes | Epsilon, rounding, cache layout and register allocation |

The remaining mapping is supported by the paged-attention interface, stateful convolution contract and fused norm/RoPE/cache API. These are useful building blocks, but equal tensor shapes alone do not imply equal state or bits. ([Unified attention](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/attention/unified_attention.py#L427-L495), [Causal convolution update](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/causal_conv1d_update.py#L12-L58), [Fused QK/RoPE/cache](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/fused_qk_norm_rope_cache_quant.py#L52-L114))

## Persistent layers and window masks leave engine work

AITER's MegaMoE TP is genuine persistent execution: one launch covers an MoE layer's two GEMMs, activation and surrounding tensor-parallel collectives. This supports the same broad motivation as K3—moving coordination onto the device—but at layer scope. Its current contract specifies gfx950, shuffled MXFP4 weights, exclusive GPU use and a two-second watchdog. Those assumptions differ from Caminus's whole-model tape and display-card safety limits; it is currently a scheduling reference rather than an executable replacement for this machine. ([MegaMoE TP contract](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/flydsl/mega_moe_tp.py#L3-L40), [Caminus safety invariants](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/AGENTS.md))

Communication deserves the same per-path treatment. AITER's generic custom allreduce explicitly avoids peer atomics because of PCIe limitations; it is inaccurate to label the entire communication library XGMI-only. Conversely, its newer Lamport path is gated to gfx942/gfx950, and no evidence here validates it on the mixed Radeon pair. Caminus's existing exchange has a specified timeout and adds card 0's partial first on both devices. A replacement must earn its benefit while preserving the required ordering and fault behavior. ([PCIe signal design](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/csrc/include/custom_all_reduce.cuh#L48-L55), [Lamport gates](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/dist/device_communicators/custom_all_reduce.py#L293-L313), [Caminus exchange](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/kernels/k3_xchg.h#L1-L86))

For the proposed rolling context, **AITER provides mechanisms, not the complete feature**. A sliding mask can restrict attention and a block table can map accessible KV. Caminus must still define eviction, logical versus physical positions, RoPE handling, QSA expiration, speculative-write headroom, checkpoint mappings and client compaction behavior. The present cache assumes earlier rows remain valid by position, and the live token log's length equals the processed position. Recurrent state also retains historical influence after KV eviction. These contracts do not disappear by swapping attention kernels. ([Attention interface](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/attention/unified_attention.py#L427-L495), [Prompt-cache assumptions](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/cache/prompt.py#L1-L32), [Live-state invariant](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/cache/livestate.py#L1-L18), [Recurrent update](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/kernels/k3_q35_ops.h#L197-L213))

One naming trap is especially relevant: unified attention's `sinks` tensor contains per-head logits contributing softmax normalization mass. It is not a set of permanently retained prefix-token KV rows. A retained system prompt or StreamingLLM-style prefix therefore needs explicit implementation beyond passing this argument. ([Sink implementation](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/_triton_kernels/attention/unified_attention.py#L228-L244))

## Reuse should begin at existing prefill boundaries

My engineering recommendation is to **keep K3's execution contract and investigate one named AITER opportunity at a time**. There are three different choices: call a compatible upstream operator at an existing launch boundary; port selected source into Caminus; or study an algorithm and implement it for the current formats. Prefill already has separate matrix/attention launches, making it a cleaner first boundary than inserting independent operator calls between decode tape tasks. A device-body port into K3 instead has to fit its dependency protocol, scratch space and shared register budget. ([Existing prefill interface](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/mmq.py#L28-L46), [K3 capability checks](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/engine/k3.py#L1365-L1383))

The following priority order is an inference from compatibility and likely integration effort, **not a profile-backed speed ranking**.

| Priority | Investigation | Adoption form | Evidence needed before adoption |
|---|---|---|---|
| 1 | QSA scoring and selection | Algorithm/reference comparison; isolate compatible stages | Selected IDs, ties and causal tails; long-context quality and time including conversions |
| 2 | Full-attention prefill and split-KV | Optional direct operator or source-port experiment | Actual shapes/cache format, logits, total prefill latency and memory |
| 3 | Chunked GDN prefill and convolution | Algorithm study or source port | Final recurrent states, checkpoint resume, verify behavior and total prefill benefit |
| 4 | Existing FP16/BF16 projections | Direct optional prefill baseline | Exact projection sizes, output precision, warmed timing and adapter costs |
| 5 | Norm/RoPE/cache fusion | Port a specific beneficial fusion | Rounding, eliminated traffic and unchanged register/spill limits |
| 6 | MegaMoE and communication design | Scheduling reference first | RDNA portability, PCIe behavior, reduction order and complete-pass timing |

The direct GEMM candidate has current gfx1100 configurations, but should target weights already stored in compatible precision. It should not begin by expanding the entire quantized model. Chunked GDN also requires an intentional numerical decision: Caminus's q3m/q35own WMMA prefill GEMMs already use model-quality gates rather than bitwise decode equality, while other operations retain stricter contracts. Existing source-specific exceptions are the authority; a blanket claim that all prefill must be bitwise would be wrong. ([A16W16 interface](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/gemm/basic/gemm_a16w16.py#L77-L136), [Current gfx1100 tuning](https://github.com/ROCm/aiter/tree/37da1dbeb305e868dda2e52d0d084a30fd71a99c/aiter/ops/triton/configs/gfx1100/triton/gemm/gemm_a16w16), [Q3MoE exception](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/q3m.py#L16-L17), [Qwen35 exception](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/python/caminus/prefill/q35own.py#L19-L22))

An eventual experiment should pin the upstream backend and commit, keep installation changes isolated, and compare the final path on the same cards, model, quantization, batch, context, memory residency and drafter settings. Include conversions, allocations, synchronization and handoff costs. Report decode and prefill separately. Caminus requires interleaved A/B measurements, medians of at least three runs and a difference above its reporting threshold; quantized-math changes additionally require per-op accuracy, model, self-consistency and shipping-module speed gates. Changed kernels need object/register evidence before guarded, small-input runs on the non-display card. No such experiment was performed in this research. ([Quantized-math gates](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/docs/specs/spec-own-quant.md#L45-L98), [Repository measurement and safety rules](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/AGENTS.md))

Source reuse has a tractable provenance path: AITER's top-level license is MIT, while Caminus declares AGPL-3.0-or-later and requires retained notices plus a third-party inventory entry for added external code. Check the selected file, dependencies, submodules and any binary artifact separately; the top-level license should not be assumed to cover every bundled component. This is implementation guidance, not a legal review of a chosen integration. ([AITER license](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/LICENSE), [AITER submodules](https://github.com/ROCm/aiter/blob/37da1dbeb305e868dda2e52d0d084a30fd71a99c/.gitmodules), [Caminus license declaration](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/pyproject.toml#L9-L16), [Third-party rules](https://github.com/jdominick05/caminus/blob/25419fb8cc3a36109a2d2bc5ef4cb8aa2e709b62/THIRD_PARTY.md#L1-L9))

Caminus's useful distinction is the combined contract it already enforces: specific GGUF models, whole-pass scheduling, a mixed Radeon pair, recurrent/cache recovery and an application-facing service. AITER's expanding coverage creates pressure to compare and improve individual implementations, while making it less sensible to recreate every optimization in isolation. The next concrete research-to-code step should therefore be a small compatibility harness for one prefill/QSA stage with a measurable bottleneck, rather than committing to a new backend for the entire engine.
